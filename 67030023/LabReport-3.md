## 2. บันทึกผลกิจกรรมนิติวิทยาศาสตร์ 3.1: การตรวจวัดความหน่วงเวลาเชิงนิติวิทยาศาสตร์ (End-to-End Latency Forensics)

### 1. ผลการบันทึกเวลาในระบบ (Timeline Log Tracing)
- **$T_0$ (จังหวะหมุน Potentiometer / อ่านค่า ADC สดบน ESP32):** `1700000000000 ms`
- **$T_1$ (Kestrel Web Server รับ HTTP/JSON Payload จาก ESP32):** `1700000000025 ms` ($\Delta T_{network} = 25\text{ ms}$)
- **$T_2$ (ESP32 รับคำสั่งตอบกลับและสั่ง OLED Flush หน้าจอเสร็จสิ้น):** `1700000000042 ms` ($\Delta T_{display} = 17\text{ ms}$)

### 2. การคำนวณความหน่วงรวมของระบบ (End-to-End Latency)
$$\Delta T = T_2 - T_0 = 1700000000042 - 1700000000000 = 42\text{ ms}$$

### 3. การวิเคราะห์และประเมินผลมาตรฐาน Real-time
จากการวัดความหน่วงรวม ($\Delta T$) ได้ค่า **42 ms** ซึ่ง **ต่ำกว่าเกณฑ์มาตรฐาน 100 ms** สำหรับการตอบสนองแบบ Real-time ทางกายภาพ ระบบจึงมีความลื่นไหลสูง ผู้ใช้งานไม่รู้สึกถึงความล่าช้า (Lag) ขณะหมุนปรับค่าเซนเซอร์

## 3. คำตอบคำถามท้ายการทดลองเพื่อการประเมินผล (Review Questions)

### ข้อ 1: หากการแสดงผลบนหน้าจอ OLED มีความล่าช้า (Lag) กว่าหน้าเว็บอย่างเห็นได้ชัด ความล่าช้านั้นน่าจะเกิดจากจุดคอขวด (Bottleneck) ใดในระบบ?
**คำตอบ:**
ความล่าช้าอาจเกิดจากจุดคอขวดหลักดังต่อไปนี้:
1. **คอขวดที่การส่งถ่ายข้อมูลสู่หน้าจอ (Display Transfer Bottleneck):** การเรียกใช้ฟังก์ชันวาดพิกเซลและ Flush บัฟเฟอร์ขนาด 1KB สู่ GRAM บนชิป SSD1306 บ่อยเกินไป หรือใช้ความถี่สัญญาณนาฬิกาบนบัสต่ำเกินไป
2. **คอขวดจากการบล็อกการทำงานใน Task (Blocking Task / Delay):** มีการใช้ฟังก์ชันหน่วงเวลาประเภท Blocking เช่น `vTaskDelay()` หรือ `delay()` ใน Loop การประมวลผลหลัก ทำให้กระบวนการอ่านค่าและส่งข้อมูลขัดจังหวะกันเอง
3. **คอขวดระดับเครือข่ายและการรอคอย HTTP Response (HTTP Transaction Overhead):** ESP32 ต้องรอคอยผลตอบกลับ (Blocking I/O) จาก Kestrel Web Server นานเกินไปก่อนที่จะไปอัปเดตหน้าจอ OLED

### ข้อ 2: เหตุใดการใช้บัส SPI 10 MHz จึงช่วยลดความหน่วงเวลาในการอัปเดตหน้าจอ OLED ได้ดีกว่าการใช้บัส I2C 100 kHz ในระบบ Closed-Loop เช่นนี้?
**คำตอบ:**
1. **ความเร็วในการส่งถ่ายข้อมูลสูงกว่ามาก (Significantly Higher Bandwidth):** บัส SPI ที่ความถี่ 10 MHz มีความเร็วในการส่งข้อมูลมากกว่าบัส I2C ที่ความถี่ Standard 100 kHz ถึง **100 เท่า** (10 Mbps vs 100 kbps)
2. **เวลาในการยิง Framebuffer สั้นกว่า:** การส่งข้อมูล Framebuffer ขนาด 1KB (8,192 บิต)
   - บนบัส I2C 100 kHz จะใช้เวลาประมวลผลส่งข้อมูลประมาณ **80–100 ms** ต่อเฟรม
   - บนบัส SPI 10 MHz จะใช้เวลาส่งข้อมูลเพียงประมาณ **1 ms** ต่อเฟรมเท่านั้น
3. **ลด Overhead ของโปรโตคอล:** บัส I2C ต้องมีบิต ACK/NACK และการจ่าหน้า Device Address ทุกๆ ไบต์ ในขณะที่ SPI ใช้สายสัญญาณ Chip Select (CS) และ Data/Command (DC) ควบคุมโดยตรง ทำให้ไม่เสียเวลาจัดการ Protocol Header ช่วยให้การอัปเดตจอภาพแบบ Real-time Closed-Loop มีความหน่วงต่ำที่สุด
